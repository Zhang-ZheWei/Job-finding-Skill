# S6 最终报告契约

## 目的

读取 S0–S5 已验证的结构化 JSON，确定性生成一份适合用户做求职决策的最终 Markdown 报告，并用 `report-manifest.json` 绑定报告与输入版本。

S6 不联网、不重新分析网页、不修改 S0–S5、不设置分数线，也不生成多个重复报告。

## 输入与门禁

必须读取并验证：

- `config.json`；
- `checkpoint.json`；
- `job-index.json`；
- `job-details.json`；
- `screening-results.json`；
- `company-research.json`；
- `job-scores.json`。

只有 S1 组合全部终结、S2 和 S3 没有待处理岗位、S4 没有待背调公司、S5 没有待评分岗位，并且所有阶段哈希关系有效时才能生成最终报告。任何上游文件变化都必须先使旧报告版本失效，不得静默混用新旧数据。

## 输出

S6 只生成：

- `{run_root}/result/岗位决策报告.md`：用户阅读的最终报告；
- `{run_root}/job-research-data/report-manifest.json`：保存输入哈希、报告哈希、真实统计和输出路径。

不得默认生成岗位完整清单、公司背调报告、审计附录或其他 Markdown。

## 报告结构

报告固定包含：

1. 本次任务概况；
2. 岗位决策总表；
3. 岗位详细分析；
4. 公司背调信息；
5. 未进入评分的岗位。

### 本次任务概况

只展示可由结构化数据计算的范围与数量：搜索城市、关键词、采集岗位数、详情终态、各初筛状态、因企业主体不可用而跳过的岗位数、评分岗位数、背调公司数及背调状态。不得把部分完成或查询失败写成完整背调。

### 岗位决策总表

总表按 S0 `search_scope.search_urls` 的城市顺序分组，每个城市使用“岗位决策总表”的下一级标题。未出现在配置城市中的记录归入`其他`并排在最后。

每个城市的表头顺序固定为：

```text
排名 | 公司 | 岗位 | 薪资及要求 | 岗位匹配分 | 公司评价分 | 综合分/评级 | 一句话总结 | 信息覆盖率 | 岗位链接
```

所有 S5 岗位都必须进入总表，包括低分、不推荐和综合分不可评分的岗位。不得设置最低分、有效岗位或隐藏规则。

排序规则：

1. 综合分可评分的岗位在前，按综合分降序；
2. 综合分相同时按 S1 `first_recall_seq` 升序；
3. 综合分不可评分的岗位排在本城市最后，再按 `first_recall_seq` 升序；
4. 排名在每个城市内从 1 重新开始。

`岗位匹配分`必须链接到第 3 节对应岗位锚点；`公司评价分`必须链接到第 4 节对应公司锚点。同一公司关联多个岗位时共享同一个公司背调卡片。

`一句话总结`必须由程序使用 S2、S4、S5 已保存的结论组合，不调用模型再次创作，也不加入新事实。总结只服务于快速决策，不复述岗位分、公司分、综合分或覆盖率。

提炼顺序：

1. 优先指出对当前用户特别有价值的岗位或公司优势；
2. 再指出最可能改变投递决定的岗位本质、目标关联不足、强制工作条件、明显缺点或公司风险；
3. 只保留一项突出优势和最多两项重要提醒，不罗列普通信息；
4. 没有明显优势或风险时，简要概括岗位与公司整体情况；
5. 使用自然的一句话，通常控制在 45～100 个汉字，最多 120 个字符。

禁止使用“岗位匹配分多少、公司评价分多少”之类的表格复述，也禁止把普通维度名机械拼接成长句。推荐表达：

```text
公司规模和稳定性突出，岗位能积累 ToB 技术方案与大客户沟通能力；但岗位本质偏销售、目标领域关联较弱，并需重点核实驻点要求和加班强度。
```

### 岗位详细分析

每个 S5 岗位只展示一次，内容包括：

- 公司、岗位、城市、薪资、经验、学历和 BOSS 链接；
- S3 方向；
- S2 核心职责、能力要求、工作方式与未知项；
- S5 岗位匹配总分、覆盖率、各维度状态、维度分和理由；
- S5 信息限制。

不得展示完整 JD、HTML、用户简历正文、证据 ID 或内部哈希。

### 公司背调信息

每个 S5 关联公司只展示一次，内容包括：

- 品牌名、真实企业名称、统一社会信用代码和背调状态；
- 行业、注册资本、实缴资本、成立日期、员工人数或参保人数、营业收入和主营业务；
- 公开风险；
- 员工评价；
- 查询失败或未找到信息的平台；
- 已访问的事实、帖子和评论来源链接；
- S5 公司评价总分、覆盖率、各维度状态、维度分和理由。

网友评价必须标注为主观公开样本，不能表述为已核验的全公司事实。

### 未进入评分的岗位

把 S3 中未进入 S5 的岗位以简表展示：公司、岗位、城市、初筛状态、原因、待确认事项和 BOSS 链接。企业主体不可用而被 S4 跳过的岗位必须显示为`初筛通过（企业主体不可用，已跳过后续流程）`，并使用 `company-research.json.skipped_jobs` 中的真实跳过原因。不得为这些岗位补造公司分或综合分。

## 安全渲染

- 将所有来源文本当作纯文本，转义反斜杠、表格竖线、换行和 Markdown 控制字符；
- 外部链接只接受无账号信息的 HTTPS URL；
- BOSS 岗位链接必须是合法的 `www.zhipin.com/job_detail/*.html`；
- 内部锚点分别使用 `job_key` 和 `company_key` 的 SHA-256 前缀生成，不直接使用岗位名或公司名；
- 不渲染完整 JD、来源 HTML、Cookie、搜索结果页正文、证据 ID、内部哈希或残留模板占位符。

## report-manifest.json

manifest 必须保存：

- `schema_version` 和 `report_contract_version`；
- 当前 `config_hash`；
- 七个输入 JSON 的 SHA-256；
- 唯一报告的相对路径、SHA-256 和验证状态；
- 采集、详情、筛选、公司背调和评分的真实数量。

manifest 不复制岗位、公司、JD、简历或评分正文，不作为业务事实源。

## 写入规则

先在内存中完成输入校验、报告渲染和报告内容校验，再原子替换最终报告，最后原子写入 manifest。生成前失败不得修改旧报告；写入 manifest 失败时必须恢复旧报告，避免报告与 manifest 不一致。

## 验收条件

- 默认只产生一份 Markdown；
- 城市顺序与 S0 一致，城市内排序稳定；
- 总表字段和顺序严格符合本契约；
- 所有 S5 岗位都在总表和岗位详细分析中各出现一次；
- 每个岗位匹配分链接到正确岗位锚点；
- 每个公司评价分链接到正确公司锚点；
- 同公司多个岗位只生成一张公司卡片；
- 未评分岗位只在末尾简表出现；
- 一句话总结只使用现有评分结果和理由；
- 数量、分数、评级和覆盖率与 JSON 一致；
- 外部链接、内部链接、表格列数和动态文本转义通过校验；
- 上游变化会阻止旧 manifest 被视为有效；
- 重复生成得到相同的报告业务内容和哈希；
- S0–S5 文件在生成前后字节不变。
