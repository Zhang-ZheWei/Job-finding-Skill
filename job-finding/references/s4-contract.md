# S4 公司网络背调契约

## 目的

只对 S3 `初筛通过`且已取得可信企业名称的岗位关联企业进行网络背调，保存公司基本信息、公开风险和员工评价的结构化事实。企业主体不可用的岗位保存结构化跳过原因，不阻断其他企业。S4 不重新判断岗位、不评分、不生成 Markdown 报告。

## 输入与门禁

- S0 `config.json`、S2 `job-details.json` 和 S3 `screening-results.json` 必须通过校验；
- S1 所有搜索组合必须为 `completed` 或 `skipped_target`，不得在目标模式的中间批次提前启动 S4；
- S3 必须没有待筛岗位；
- 只处理 `status=初筛通过` 的岗位；
- 企业名称和统一社会信用代码只读取 S2 BOSS 工商主体，不根据招聘品牌或网络搜索结果猜测；
- S2 未取得可信企业名称、查询失败或来源冲突时，不生成公司任务；程序将该岗位写入 `skipped_jobs` 并继续处理其他岗位；
- 同一统一社会信用代码只生成一个公司任务；代码缺失时按规范化企业名称去重；
- 每次只处理首个待背调公司，不得跳过或重排。

S4 `pending` 返回公司身份、关联岗位、S0 `company_preferences`、去重后的 `search_terms` 和完整 `required_queries`。搜索词固定包含真实企业名称和 S2 中每个不同的招聘品牌名；这些偏好只决定重点查什么，不自动生成新的淘汰规则。

## 联网规则

调用 `$web-access`，按企业全称进行查询。一次只处理一家公司，浏览器中最多保留一个任务标签页。

背调固定包含三个组：

1. `basic_profile`：必须分别用真实企业名称查询爱企查和公司官网。爱企查只采集行业、注册资本、实缴资本、成立日期、人员规模、营业收入和企业简介；企业简介只用于分析主营业务。基本信息同时参考爱企查与官网；没有可确认官网时记录`未找到相关内容`，并主要根据爱企查判断；
2. `public_risks`：司法、行政处罚、监管措施、经营异常、劳动争议、财务或声誉风险；
3. `employee_reviews`：必须在知乎、小红书、牛客网、脉脉四个平台，分别使用每个品牌名和真实企业名称查询。每次查询都要检查相关帖子及其评论，再总结工作强度、管理、薪酬、成长、稳定性和文化等真实网友评价。

爱企查和公司官网用于公司基本信息；政府、法院、监管机构和其他一手来源用于公开风险。不得读取或保存爱企查的自身风险、关联风险等平台统计，也不得将其作为公开风险查询证据。搜索页只证明已经执行查询，不能直接证明事实。网友评价必须引用实际打开的帖子或评论，并明确当作主观公开评价，不写成已核验公司事实。

爱企查字段必须按以下方式解释：

- 工商注册页的`参保人数`只能保存为参保人数，不能改写成员工人数；上市信息明确披露`员工人数`时才保存为员工人数；
- 普通企业优先从企业年报读取`销售总额`或`主营业务收入`，上市企业可从财务指标或利润表读取`营业总收入`；
- 页面显示`不公示`、`-`或没有对应字段时，保存为未披露，不得根据公司规模、注册资本或网络描述推算；
- 企业简介和经营范围用于概括主营业务，但必须保留“官网自述”“平台简介”或“工商经营范围”等来源性质，不能把宣传性描述写成已核验经营成果。

平台查询必须通过真实搜索框提交。结果页加载后同时核对页面显示的关键词与 `required_queries.search_term` 完全一致，并复制浏览器最终 `location.href` 作为 `search_url`。不得猜测站点路径、手工拼接 URL 或手工进行百分号编码。若正确搜索完成但没有相关帖子，记录`未找到相关内容`；只有正确搜索无法执行或结果页无法读取时才记录`查询失败`。

## 模型提交

模型通过标准输入提交：

```json
{
  "company_key": "pending 返回的公司键",
  "query_attempts": [
    {
      "group": "employee_reviews",
      "platform_key": "zhihu",
      "platform": "知乎",
      "search_term": "企业品牌名",
      "search_term_type": "brand_name",
      "result_status": "找到相关内容",
      "search_url": "https://www.zhihu.com/search?...",
      "content_types_reviewed": ["post", "comment"],
      "note": "已打开相关帖子并检查评论"
    }
  ],
  "evidence": [
    {
      "source_ref": "s1",
      "group": "basic_profile",
      "platform_key": "aiqicha",
      "source_type": "business_information_platform",
      "platform": "爱企查",
      "title": "页面标题",
      "url": "https://example.com/page",
      "excerpt": "支持结论的有限页面摘要",
      "access_status": "已访问",
      "content_type": "page"
    }
  ],
  "basic_profile": {
    "query_status": "已完成",
    "items": [
      {
        "category": "main_business",
        "summary": "主营业务事实",
        "evidence_refs": ["s1"]
      }
    ],
    "source_evidence_refs": ["s1"],
    "failure_evidence": []
  },
  "public_risks": {
    "query_status": "已完成",
    "items": [],
    "source_evidence_refs": ["s2"],
    "failure_evidence": []
  },
  "employee_reviews": {
    "query_status": "部分完成",
    "items": [
      {
        "category": "work_intensity",
        "summary": "网友帖子和评论反映的主观体验",
        "evidence_refs": ["post1", "comment1"]
      }
    ],
    "source_evidence_refs": ["post1", "comment1"],
    "failure_evidence": [
      {
        "platform": "平台名称",
        "url": "https://example.com/blocked",
        "reason": "访问受限"
      }
    ]
  }
}
```

`query_attempts`必须逐项对应 `pending.required_queries`，不能遗漏、增加或重复。状态只能是`找到相关内容`、`未找到相关内容`或`查询失败`。网友评价查询的 `content_types_reviewed` 必须同时包含 `post` 和 `comment`。

网友评价 `search_url` 必须属于对应平台、使用浏览器返回的规范编码形式，并在解码后包含该项 `search_term`。这只是最低结构校验；Agent 仍必须在浏览器中核对页面确实完成了该次搜索。

`source_ref`只是当前提交内的引用，程序生成稳定 `evidence_id`。每条事实只能引用同组来源。公司基本信息事项只能引用爱企查或官网；网友评价事项只能引用知乎、小红书、牛客网或脉脉的帖子、评论原页。模型不得提交公司身份、配置哈希、输入哈希、阶段状态、版本、数值置信度、覆盖率或风险分数。

## 状态语义

- `已完成 + items=[]`：已经查询，并有来源证明查询动作，但没有发现可保存的可靠结果；
- `部分完成`：固定查询清单中有部分平台失败，但其他平台已完成；必须填写 `failure_evidence`；
- `查询失败`：固定查询清单全部失败、无法完成查询或没有取得可核验来源，必须填写 `failure_evidence`；
- 有事实或风险事项时，每项必须引用至少一个同组、已成功访问的来源；
- 三组均完成时公司状态为`已完成`；部分组失败时为`部分完成`；三组均失败时为`查询失败`。

爱企查找到企业且官网找到或确认不存在时，基本信息可以完成；爱企查失败但官网可用时只能部分完成。网友评价四个平台的所有“平台 × 搜索词”组合均无失败时才算完成。

多个来源冲突时分别保存支持各自说法的事项，并在摘要中明确冲突，不擅自选择一个结论。

## 输出

S4 只新增 `{run_root}/job-research-data/company-research.json`。顶层保存 S0 `config_hash`、S2 输入哈希、完整 S3 结果哈希和程序生成的 `skipped_jobs`。`skipped_jobs` 保存岗位键、BOSS 公司主体键、主体状态、原因代码和原因；S5 不处理这些岗位，S6 必须展示跳过原因。每家公司保存：

- 稳定公司键、企业名称、统一社会信用代码；
- BOSS 工商主体键、招聘品牌、关联岗位和报告城市；
- 真实企业名称与品牌名构成的搜索词；
- 爱企查、官网和四个评价平台的逐项查询记录；
- 三组查询结果；
- 有限来源证据；
- 程序生成的公司背调状态和修订版本。

不得保存整页正文、HTML、搜索结果页正文、Cookie、置信度、覆盖率或评分。

## 验收

- 只出现 S3 初筛通过岗位关联的企业；
- 企业主体不可用的初筛通过岗位被写入 `skipped_jobs`，且不会阻止其他公司进入待处理队列；
- 同一企业只背调一次；
- 企业身份与 S2 工商主体一致；
- 三个查询组都有明确终态；
- 爱企查和官网查询记录齐全；
- 爱企查只保存指定基本信息字段，不保存平台风险统计；
- 员工人数与参保人数不混用，营业收入未公示时不推算；
- 知乎、小红书、牛客网、脉脉分别使用每个品牌名和真实企业名称查询；
- 搜索 URL 来自搜索完成后的浏览器最终地址，解码后与对应搜索词一致；
- 每次网友评价查询都记录已检查帖子和评论；
- 空结果与查询失败严格区分；
- 事实引用同组合法来源，HTTPS 链接和证据关系通过校验；
- S2 或 S3 变化时阻止复用旧结果；
- 中断后从首个待背调公司继续；
- 不生成额外中间文件。
