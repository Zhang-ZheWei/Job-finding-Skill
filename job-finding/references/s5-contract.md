# S5 综合评分契约

## 目的

读取 S0–S4 已经形成的结构化事实，为进入 S5 的每个岗位计算岗位匹配分、公司评价分、综合分和证据覆盖率，输出 `job-research-data/job-scores.json`。

S5 只负责评分，不重新筛选岗位，不审核或修复前序阶段，不联网，不生成 Markdown，也不根据分数淘汰岗位。所有进入 S5 的岗位都必须写入评分结果，并在 S6 最终报告中展示。

## 输入边界

S5 使用：

- S0 `config.json`：用户画像、目标方向、工作偏好和公司偏好；
- S2 `job-details.json`：岗位职责、能力要求、工作方式、未知项和 JD 证据；
- S3 `screening-results.json`：岗位方向和已经形成的初筛结果；
- S4 `company-research.json`：公司基本信息、公开风险、员工评价和来源证据。

能够进入 S5 的岗位由前序流程和阶段门禁决定。S5 不再次判断岗位是否应该通过 S3，也不检查 S2、S3、S4 的语义结论是否正确。

S5 只做最低限度的技术校验：JSON 可以读取、必要字段和类型合法、`job_key` 与 `company_key` 可以关联、证据 ID 属于当前岗位或公司、模型选择的维度和锚点属于本契约。技术校验失败时停止并报告数据错误，不跨阶段修复。

## 通用性

评分维度、权重和锚点固定，具体判断条件从当前 S0 动态生成。不得把测试用户的学历、岗位方向、能力、城市、行业或公司偏好写入 Skill 默认规则。

程序在 `pending` 输出中生成只读 `scoring_context`：

- 岗位目标条件来自 `job_target.target_directions`、`desired_work_features` 和 `soft_preferences`；
- 用户能力条件来自 `candidate_profile`；
- 公司判断条件来自 `company_preferences`，并可结合已确认的目标方向；
- 每条条件由程序生成稳定 `criterion_id`，模型只能引用，不得改写配置或增加条件。

硬性岗位要求和 `hard_exclusions` 已由 S3 处理，不作为 S5 评分维度。S5 不因岗位已经通过硬性条件而重复加分。

## 评分结构

综合分由岗位匹配度和公司评价组成：

```text
岗位匹配度系数 = 0.70
公司评价系数   = 0.30
```

### 岗位匹配度

| 维度 ID | 名称 | 权重 | 判断内容 | 允许引用的事实 |
|---|---|---:|---|---|
| `target_and_responsibility_fit` | 目标方向与核心职责匹配 | 4.0 | 核心职责与用户目标方向、期望工作特征的匹配程度 | S2 岗位证据、S3 岗位方向 |
| `strength_utilization` | 用户能力与优势发挥 | 3.0 | 岗位能否实际使用用户已经确认的知识、能力、经验和职业优势 | S2 岗位证据、S0 候选人条件 |
| `work_style_fit` | 工作方式与偏好匹配 | 2.0 | 工作性质、协作方式、工作强度及其他已确认软偏好的匹配程度 | S2 岗位证据和未知项、S0 工作偏好 |
| `role_growth_fit` | 岗位成长与职业延续性 | 1.0 | 岗位本身是否有助于积累目标能力并延续用户期望方向 | S2 岗位证据和未知项、S0 发展偏好 |

岗位组权重合计必须为 10。

### 公司评价

| 维度 ID | 名称 | 权重 | 判断内容 | 允许引用的事实 |
|---|---|---:|---|---|
| `business_and_industry_fit` | 主营业务与行业匹配 | 2.5 | 公司主营业务、行业和业务方向与用户目标及公司偏好的匹配程度 | S4 `basic_profile` |
| `scale_and_stability` | 经营规模与稳定性 | 2.0 | 成立时间、明确披露的员工人数或参保人数、营收、注册资本和实缴资本反映的经营基础；未披露字段不按零分处理 | S4 `basic_profile` |
| `employee_experience_and_culture` | 员工体验与企业文化 | 3.0 | 工作强度、管理、薪酬、稳定性和文化等公开员工体验与用户偏好的匹配程度 | S4 `employee_reviews` |
| `company_growth_platform` | 成长平台与培养条件 | 1.5 | 公司是否提供用户关注的培训、成长平台和发展环境 | S4 `basic_profile`、`employee_reviews` |
| `public_risk` | 公开风险 | 1.0 | 公开风险事项对求职决策的影响程度 | S4 `public_risks` |

公司组权重合计必须为 10。

`role_growth_fit` 判断岗位工作本身能积累什么；`company_growth_platform` 判断公司能提供什么平台和培养条件，两者不得混用同一结论。

## 评分锚点

除公开风险外的维度使用统一锚点：

| 锚点 | 系数 | 使用条件 |
|---|---:|---|
| `strong_match` | 1.00 | 有直接、充分证据表明强匹配 |
| `match` | 0.80 | 主要条件匹配，未见明显不利证据 |
| `partial_match` | 0.50 | 同时存在匹配与不足，或只覆盖部分条件 |
| `weak_match` | 0.20 | 只有较弱、次要或间接匹配 |
| `mismatch` | 0.00 | 有直接证据表明不匹配 |

公开风险维度使用：

| 锚点 | 系数 | 使用条件 |
|---|---:|---|
| `no_material_concern` | 1.00 | S4 已完成规定查询，未发现实质性风险事项 |
| `minor_concern` | 0.75 | 存在轻微或对求职影响有限的风险信号 |
| `moderate_concern` | 0.40 | 存在需要用户重点权衡的风险事项 |
| `major_concern` | 0.00 | 存在可能显著影响求职决策的重大风险事项 |

模型只能选择锚点，不能提交系数、维度分、组分、综合分或覆盖率。锚点必须有当前维度允许使用的证据支持；不得因为公司知名、岗位标题好听或常识推测而选择锚点。

## 信息不足

每个维度只有两种状态：

- `可评分`：存在足够证据，必须选择一个合法锚点并引用证据；
- `不可评分`：信息缺失、证据不足或现有冲突无法支持稳定判断，不选择锚点。

`不可评分`不得按零分处理。其权重由程序按原始权重比例分配给同组其他可评分维度：

```text
有效权重 = 10 × 当前维度原始权重 ÷ 当前组可评分维度原始权重之和
组分 = Σ(有效权重 × 锚点系数)
```

证据覆盖率单独计算：

```text
组证据覆盖率 = 当前组可评分维度原始权重之和 ÷ 10
综合证据覆盖率 = 岗位组覆盖率 × 0.70 + 公司组覆盖率 × 0.30
```

覆盖率只表示分数由多少预设维度的信息支撑，不代表模型置信度，不触发复核、补查、淘汰或返回前序阶段。

如果一个组没有任何可评分维度，该组分为 `null`。只有岗位组和公司组都能计算组分时才计算综合分；不得把缺失组的系数转移给另一组。综合分无法计算时，岗位仍然写入 `job-scores.json` 并进入最终报告。

## 综合分与评级

```text
综合原始分 = 岗位匹配分 × 0.70 + 公司评价分 × 0.30
```

所有最终显示分数使用 Decimal `ROUND_HALF_UP` 保留一位小数。

| 分数范围 | 评级 |
|---|---|
| 8.5–10.0 | `强匹配` |
| 7.0–低于 8.5 | `匹配` |
| 5.5–低于 7.0 | `可考虑` |
| 4.0–低于 5.5 | `弱匹配` |
| 0–低于 4.0 | `不推荐` |

评级只用于解释和排序，不是筛选门槛。不得生成 `is_effective`、`validity_status`、最低入选分或其他淘汰字段。

## 模型提交

模型只提交当前岗位的维度判断：

```json
{
  "job_key": "id:example",
  "job_match": [
    {
      "dimension_id": "target_and_responsibility_fit",
      "status": "可评分",
      "matched_anchor": "match",
      "criterion_ids": ["criterion_id"],
      "evidence_ids": ["S2 evidence_id"],
      "reason": "有限、可追溯的判断理由"
    }
  ],
  "company_evaluation": [
    {
      "dimension_id": "public_risk",
      "status": "不可评分",
      "matched_anchor": null,
      "criterion_ids": ["criterion_id"],
      "evidence_ids": [],
      "reason": "没有足够公开信息支持风险档位"
    }
  ]
}
```

两个数组必须各自完整提交本契约规定的全部维度，不能遗漏、增加、重复或调整顺序。岗位维度只能引用当前岗位的 S2 证据；公司维度只能引用当前关联公司的 S4 证据。`不可评分`可以引用造成冲突的证据，但不能选择锚点。

模型不得提交权重、有效权重、系数、分数、评级、覆盖率、哈希、版本、阶段状态或复核字段。

## 程序生成与输出

程序生成：

- 固定原始权重和重新分配后的有效权重；
- 每个维度分、岗位组分、公司组分和综合分；
- 岗位组、公司组和综合证据覆盖率；
- 评级；
- `scoring_rule_version`、`scoring_config_hash`、输入哈希和记录修订版本；
- 由不可评分维度形成的 `information_limitations`。

`job-scores.json` 的作用是回答“基于当前结构化事实，各岗位的相对匹配程度和信息充分程度如何”。它不复制完整 JD、公司背调正文或用户简历，只保存评分结果、理由和可追溯引用。

## 禁止事项

- 不联网或重新打开任何岗位、公司、搜索结果、帖子或评论；
- 不重新判断岗位是否应通过 S3；
- 不审核、修复或退回 S0–S4；
- 不创建复核状态、复核任务或自动补查流程；
- 不把缺失信息当零分；
- 不在岗位组与公司组之间重新分配系数；
- 不按得分删除、隐藏或阻止岗位进入最终报告；
- 不生成 Markdown 或额外中间 JSON。

## 验收条件

- 评分维度和权重与本契约一致，且没有测试用户个人信息；
- 硬性条件不重复参与评分；
- 模型只提交合法锚点、理由和当前记录证据；
- 所有数学结果都可由程序从输入重新计算；
- 不可评分维度在组内按比例重新分配权重，同时降低覆盖率；
- 单组完全不可评分时不进行跨组权重转移；
- 不存在覆盖率门槛、复核字段或有效岗位阈值；
- 所有进入 S5 的岗位均出现在 `job-scores.json`；
- S5 不修改任何 S0–S4 文件。
